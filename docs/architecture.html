Blast Radius Engine

A tri-layer knowledge graph that connects product intent, the running UI, and the code behind it — then, given a real pull request, reports what's at risk in language a QA lead can read.

Deterministic spine · LLM only at the seams — graph, crawl, diff & traversal are reproducible; the model is used only where semantic judgment is unavoidable.

Graph schema

Node types

Requirement Screen UIElement UIFlow CodeSymbol Gap

Edge types

  • Screen ─CONTAINS→ UIElement
  • UIElement ─TRANSITIONS_TO→ Screen
  • UIFlow ─STEP→ UIElement
  • UIElement ─IMPLEMENTED_BY→ CodeSymbol
  • CodeSymbol ─DEPENDS_ON→ CodeSymbol
  • Requirement ─VERIFIED_BY→ UIElement
  • Requirement ─HAS_GAP→ Gap

◇ Modeling absence as a positive assertion

A missing edge is ambiguous — it can't be told apart from "not analyzed yet." So absence is recorded, not inferred: Requirement.coverage ∈ {verified, partial, absent, ambiguous} plus an explicit (Requirement)-[:HAS_GAP]->(:Gap) node storing the best candidate found and its sub-threshold score.

This makes absence queryable and auditable — and it can even surface in a blast radius: a PR touching the only code tentatively linked to an already-absent requirement.
